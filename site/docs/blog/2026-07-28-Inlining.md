# Inlining policy

vecxt uses Scala 3's `inline` heavily in some places and deliberately not at all in others. This page explains the rule, why it is drawn where it is, and what went wrong when it was not.

If you are contributing a new operation, the short version is at the bottom.

## The rule

> Use `inline` when the compiler erases something the JIT cannot recover: **closure identity**, a **compile-time constant**, or a **concrete type**. Do not use `inline` merely to avoid a call.

Everything below is justification for that sentence.

## Two different inliners

It is tempting to reason that "inlining is nearly always a win, so `inline` everywhere is nearly always a win." The premise is true and the conclusion does not follow, because the folklore is about a different mechanism.

| | Scala 3 `inline def` | HotSpot C2 |
|---|---|---|
| When | Compile time, on trees | Runtime, on bytecode |
| Policy | Unconditional | Budgeted — can decline |
| Information used | None | Type profiles, branch frequencies, call counts |
| Effect on bytecode | Duplicates it per call site | Only reads it |
| Per-call-site decision | No — same everywhere | Yes |

C2's inlining is nearly always a win *because of the selectivity*, not because of the inlining. It inlines what is hot and small, declines what is not, and decides separately at each call site using data that does not exist at compile time.

Scala's `inline` keeps the expansion and discards the selectivity. That is not "more inlining"; it is a strictly less informed policy applied unconditionally.

They are also not additive. Scala's `inline` spends the budget C2's inliner needs:

- **`FreqInlineSize` (325 bytecodes).** A method larger than this will not be inlined into *its* caller. Duplicating loop bodies into user code means our inlining blocks theirs.
- **`MaxInlineLevel` (15).** The Panama Vector API works by inlining a deep chain of `@ForceInline` intrinsics. When that chain runs out of depth, `DoubleVector` stops being a register-resident value and becomes a heap allocation per operation.
- **`HugeMethodLimit` (8000 bytecodes).** Past this, `DontCompileHugeMethods` means C2 **refuses to compile the method at all**. It runs interpreted forever, silently, with nothing in a profile pointing at vecxt.

That last one is the reason this matters for a library rather than for one codebase. A user writing a large numeric kernel can fall off that cliff without doing anything wrong, and has no way to diagnose it without `-XX:+PrintCompilation`.

## Where `inline` is not negotiable

For a family of methods, `inline` is doing work no JIT can do, and removing it would be a serious regression. These stay.

### Higher-order functions

```scala
inline def reduce(inline f: (Double, Double) => Double): Double
```

Without `inline`, `f.apply` is a real call site. Called from several places with different lambda classes it becomes **megamorphic**: C2 gives up past two receiver types and emits a virtual call it will not inline. Nothing downstream survives that — no scalar replacement, no optimisation across the call boundary.

With a generic element type it is worse. Scala 3 has **no `@specialized`**, so `f: A => B` erases to `Function1[Object, Object]` and every primitive boxes on every element. No specialised `JFunction` variant helps, because `A` is not known at the definition site.

`inline` erases the closure entirely. The body is spliced in, the lambda never exists, nothing boxes, and there is no call site to be megamorphic. This is the strongest case for `inline` in the language and vecxt relies on it throughout the `ndarray` layer.

### Operator dispatchers

```scala
private inline def logicalIdx(inline op: VectorOperators.Comparison, num: Double): Array[Boolean] =
  ...
  inline op match
    case VectorOperators.LT => while i < n do idx(i) = vec(i) < num; i += 1
    case VectorOperators.GT => ...
```

Two things depend on `inline` here. The `inline op match` reduces at compile time to exactly one tail loop — and note that a non-reducible `inline match` is a **compile error**, not a silent runtime fallback, so this reduction is guaranteed rather than hoped for. And the Vector API only intrinsifies when the operator reaches C2 as a constant.

De-inlining these turns `op` into a runtime parameter, at which point the vector operations quietly stop being intrinsified and fall back to generic code. **The test suite stays green.** Only `-XX:+PrintIntrinsics` or a benchmark reveals it.

### Type specialisation across erasure

```scala
protected[vecxt] object dimCheck:
  inline def apply[A, B](a: Array[A], b: Array[B]): Unit =
    if a.length != b.length then throw VectorDimensionMismatch(a.length, b.length)
```

This looks like an ideal candidate for de-inlining — ten bytecodes, called everywhere. It is not. `Array[A]` with unbounded `A` erases to `Object`, so `a.length` cannot compile to an `arraylength` bytecode; it routes through `ScalaRunTime.array_length`, a runtime match over nine array types, megamorphic when shared across the Double, Float and Int paths. `inline` keeps the concrete element type visible so `a.length` is one instruction.

## Where `inline` is not helping

For the bulk of the arithmetic surface — the element-wise operations on `Array[Double]`, `Array[Float]` and `Array[Int]` — none of the above applies:

```scala
def *(d: Array[Double]): Array[Double] =
  dimCheck(vec, d)
  val n     = vec.length
  val bound = spd.loopBound(n)
  val out   = new Array[Double](n)
  var i = 0
  while i < bound do
    DoubleVector.fromArray(spd, vec, i).mul(DoubleVector.fromArray(spd, d, i)).intoArray(out, i)
    i += spdl
  end while
  while i < n do
    out(i) = vec(i) * d(i); i += 1
  end while
  out
```

No closure. No type parameter. No operator to keep constant. Extension methods compile to static methods on the module class, so the call is monomorphic by construction and cannot become megamorphic. The `DoubleVector` values are born and die inside one loop iteration, so they never cross the method boundary and escape analysis sees the same graph either way.

These are plain `def`s. C2 inlines them when they are hot, per call site, with better information than we have.

### On escape analysis specifically

A common argument for `inline` around Panama is that the vector values are box-like pre-Valhalla, so inlining is needed to keep them in registers. Escape analysis runs on C2's IR *after* C2's own inlining, so the question is only ever whether **C2** inlined the call. Scala-level inlining can only help in the case where C2 would otherwise have declined — and Scala-level inlining makes methods bigger, which makes C2 more likely to decline. The mechanism undercuts itself at exactly the margin where it would matter.

Where it genuinely applies is closures, which is why the higher-order functions above keep `inline`.

## Bounds checking, and a bug worth remembering

vecxt used to carry a compile-time flag:

```scala
object BoundsCheck:
  type BoundsCheck = Boolean
  object DoBoundsCheck:
    inline given yes: BoundsCheck = true
    inline given no: BoundsCheck = false
```

Importing `DoBoundsCheck.no` erased dimension checks. Because `inline if doCheck` can only reduce if the flag is a compile-time constant at the point of expansion, every method in the chain had to be `inline` to propagate it. That single requirement is what pushed `inline` across most of the library.

It has been removed, for two reasons.

### It conflated a correctness check with an optimisation

Most members of the check family validated arguments and threw. One did not:

```scala
def apply[A, B](a: Matrix[A], b: Matrix[B])(using inline doCheck: BoundsCheck): Boolean =
  inline if doCheck then
    a.isDenseColMajor && b.isDenseColMajor && a.rowStride == b.rowStride || ...
  else true
```

This is not validation. It is **capability detection** — it answers "are these two matrices laid out such that a flat loop over the backing arrays is valid?" — and matrix element-wise operations branch on it to choose between a contiguous fast path and a stride-aware slow path.

Returning `true` unconditionally under `DoBoundsCheck.no` meant transposed, sliced, and strided matrices took the contiguous path. Wrong values, or reads past the logical extent, with no exception. Across 13 call sites and all four platforms.

The distinction is worth internalising:

- **Validation** — "throw if the caller is wrong." Optional in principle; skipping it trades a diagnostic for speed.
- **Capability detection** — "which algorithm is valid here?" Never optional. Skipping it does not lose a diagnostic; it runs the wrong code.

The two are easy to confuse when both are spelled `somethingCheck` and live in the same file.

### The checks probably paid for themselves anyway

An upfront `a.length != b.length` is exactly the fact C2 needs to prove `b(i)` is in range for `i < a.length`, and therefore to eliminate the per-access range check inside the loop. You cannot remove the JVM's own bounds checks — that is memory safety — you can only give C2 enough information to prove them redundant. The dimension check *is* that information. It is why `java.util.Arrays` does upfront checks.

So the flag plausibly cost more than it saved on two-array operations, while forcing `inline` across the whole library to exist at all.

Checks are now unconditional, and are kept in the **same method** as the loop they guard, so the length fact and the accesses are in one compilation unit.

## Loop bounds

Write the loop limit as a local `val`:

```scala
val n     = vec.length
val bound = spd.loopBound(n)
var i = 0
while i < bound do ...
```

not as `while i < spd.loopBound(vec.length) do`.

`loopBound` is `@ForceInline` and reduces to `length & -laneCount`, so in C2 steady state the difference is nil. The reason to hoist is **loop recognition**: for C2 to treat the loop as counted — and so unroll it, eliminate range checks, and align it — the limit must be provably invariant, which depends on `loopBound` having been inlined. Hoisting removes that dependency, and also removes the per-iteration call in the interpreter and C1 tiers.

For the same reason, **never read a `lazy val` in a loop condition**. Scala 3 compiles `lazy val` to a bitmap read with volatile semantics, and a volatile read is a memory barrier that C2 cannot hoist. A `lazy val` caching cheap arithmetic is a pessimisation twice over.

## Checklist for new operations

Ask, in order:

1. **Does it take a function parameter?** → `inline`, with `inline` on the parameter too.
2. **Does it need a `VectorOperators` constant, or an `inline match` on one?** → `inline`.
3. **Is it generic in a way that erases a primitive or an array element type?** → `inline`.
4. **None of the above?** → plain `def`. Hoist the loop bound. Keep the dimension check in the same method as the loop.

And separately:

5. **Am I writing something named `...Check` that returns a value the caller branches on?** → It is not a check. Name it as a predicate, keep it unconditional, and put it with the other predicates.

## Verification

```bash
# what the Scala compiler expanded, per call site
scalac -Xprint:inlining Kernel.scala

# bytecode size per method — compare against 325 and 8000
javap -c -p 'Kernel$.class' | awk '/^  [a-z].*\(/{m=$0;n=0} /^ +[0-9]+:/{n++} /^$/{if(m)print n, m; m=""}'

# C2's decisions, and whether the vector ops are still intrinsified
java -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining -XX:+PrintIntrinsics \
     --add-modules=jdk.incubator.vector ...
```

`PrintIntrinsics` is the important one. Losing intrinsification is the failure mode that does not break a single test.
